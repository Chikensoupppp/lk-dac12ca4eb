# iPhone Screen Time restrictions

Status: implemented and unit-tested; **enforcement not verified**. No signed build has run on a physical iPhone. The simulator cannot grant Screen Time access, so shields have never been applied by this code on any device.

## What the app does

- `RestrictionController` (`apps/ios/LockIn/Restrictions/`) applies shields only for apps, categories and web domains the user picked in `FamilyActivityPicker`. It never selects anything by default.
- Shields are written to one named `ManagedSettingsStore` (`lockin.focus`), so clearing it cannot touch other settings.
- Order on start: schedule a Device Activity backup interval first, then apply the shield. If scheduling throws, no shield is applied (fail closed). Status shows "Shields not started".
- Sessions shorter than 15 minutes get no shields. Apple's minimum interval is fifteen minutes (`MonitoringError.intervalTooShort`), so a shorter session has no OS-side backup removal. The picker offers 15, 25, 45, 60 and 90 minutes.
- The backup interval ends 30 seconds after the session so whole-second rounding cannot fall under the minimum.
- Removal paths: early end, natural completion, launch/foreground reconcile, revoked authorization, and the `LockInMonitor` extension (`intervalDidEnd`). All are idempotent.
- The extension ignores callbacks for unknown activities, early callbacks, and callbacks from an older session when a newer one is still monitored. Activity names encode session id and end time.

## Apple limits this design respects (from Apple documentation)

- Minimum monitoring interval: 15 minutes.
- `intervalDidEnd` runs only when the device is in use. **Removal can lag the session end** if Lock In is closed. Do not promise exact-second removal.
- `ManagedSettingsStore`: the system does not guarantee settings govern device behavior.
- With individual authorization, the system lifts protections so the user can delete the app or sign out of iCloud. **Blocking is not tamper-proof.**
- If authorization is revoked, selection tokens are voided.
- Authorization is requested with `.individual` and shows a system prompt (Face ID / Touch ID).

## Essential and emergency access

Lock In shields only what the user picks. The sheet tells the user not to pick Phone or Messages if needed. "End session" is always available in the app. Whether the system shields can ever cover Phone or emergency calling was **not tested**.

## Still required before any device test

1. Apple Developer Program membership (the owner's, paid).
2. Bundle IDs `com.brandon132199.lockin` and `com.brandon132199.lockin.monitor` are registered on the owner's team, each with Family Controls (Development) ticked. Distribution still needs Apple's approval.
3. The Family Controls capability on **both** the app and the `LockInMonitor` extension identifiers. Apple says the Account Holder must request the entitlement for distribution (and submit the same request for each extension). Request status shows as Assigned in Certificates, Identifiers & Profiles. Whether a development build needs approval first is not confirmed here; check in Xcode.
4. Automatic signing with the owner's team. Do not put certificates, keys, profiles or API keys in Git or chat.
5. A physical iPhone (iOS 17 or newer), registered for development.
6. Entitlement files are generated by XcodeGen at `apps/ios/Config/` and set `com.apple.developer.family-controls`. Simulator CI builds unsigned; this does not exercise provisioning.

## Physical-device test plan

1. Install a signed development build. Tap the shield icon, allow access, choose one harmless app.
2. Start a 15 minute session. Confirm the chosen app is shielded and others are not.
3. End early; confirm shield gone.
4. Start again, force-quit Lock In, wait past the end, use the phone; record how long until the shield clears.
5. Revoke access in Settings > Screen Time > Apps With Screen Time Access mid-session; open Lock In; confirm no stuck shield.
6. Record results in `PROJECT_STATUS.md`. Do not claim enforcement before this.
